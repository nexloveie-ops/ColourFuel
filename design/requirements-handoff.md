# ColourFuel 需求与项目交接

更新日期：2026 年 11 月 19 日。本文供 Claude、开发者和项目所有者共同使用，覆盖当前对话可见的产品需求、关键调整原因、已实现状态与未完成工作；不是逐字聊天记录，也不补写未提供的早期品牌研究或商业数据。后续用户明确指示优先，需求变化应同步维护本文。

## 1 品牌与平台定位

ColourFuel 面向爱尔兰市场，提供 Bowl 产品概念及可追溯的食物信息。用户希望客人先直观看清“会得到什么”，再理解食材、用量、酱料和营养，帮助选择和购买决策。用户提出“产品和信息的平台”这一方向；当前实现支持菜单和信息展示，但尚无真实下单、支付、履约或库存系统，不应把品牌意图写成已验证的成交率或商业结果。

用户强调累积迭代：完成新页面不能忘记、删除已有食材信息、菜谱分享、餐品定制等功能。默认使用中文与所有者交流；网站当前主要使用英文。用户倾向直接执行已授权工作，避免对已明确事项反复征求确认。

保留素食识别：Plant Power Crunch、Asian Sesame Crunch 使用 Vegan base 标记；Mediterranean Garden 为含 feta 的素食概念。说明是基础配方性质，酱料、添加食材、芝士凝乳酶及交叉接触可能改变适用性，不能承诺整碗 vegan、过敏原安全或认证。

## 3 产品页面与定制路径

用户已经选择某个产品，进入 `#bowl/<product-id>` 后就应看到该产品图片、食材、用量和 Make it yours。不应再要求点击 Build your own 或 Start from a recipe 才能查看/编辑配方。

当前客户餐品页直接调整单碗，不显示 Recipe name 和 Bowls in batch 输入框，也不重复显示“一碗总价”。用户认为它们此时没有意义。独立 Recipe Studio 用于命名、自建配方、保存、分享和批量，因此保留这些能力。不要把餐品页的精简误读成删除配方元数据或整个平台的批量功能。

保留 Original Recipe、Protein+、Active Day。它们是固定测试预设，不是健康评级或个人运动/营养处方。手动调整转为 Custom Recipe；原始配方作为比较基准。旧配方基线或批量状态不匹配时，不能强行套用新预设，应明确不可用原因。

## 4 标准份模型与厨房准确性

用户希望客人按份调整、后台按克计算、员工按统一标准制作，便于成本和售价管理。模式已确认；具体克重是实现中提出的厨房测试参数，尚未由真实厨房核定。标准由 `portion-standards.mjs` 统一定义，不能在各 Bowl 里另设同一食材的“一份”。

当前建议标准：熟鸡肉、金枪鱼、猪肉、三文鱼、熟鹰嘴豆、毛豆均为 50 g/份；熟糙米和藜麦 50 g/份，允许半份即 25 g；西兰花、胡萝卜、红椒、番茄、黄瓜、紫甘蓝、熟甜玉米 50 g/份；菠菜和 feta 25 g/份，葱 10 g/份，芝麻与橄榄油 5 g/份。其他库内食材有明确标为建议起点的标准，不能当成已验证的出品规范。

八款概念配方已显式更新为 v2，原始配方与 16 个预设均对齐当前标准。完整每碗克重见 [标准份明细](standard-portions.md)，代码以 `menu-formulations.mjs` 为准。Protein+ 增加一份 50 g 的对应蛋白/豆类，Active Day 增加一份 50 g 熟谷物。

用户明确不喜欢加减按钮，要求拖拽：食材和酱料用原生 range 滑杆，显示当前份数、每份克重和每碗克重；谷物半份移动，其余菜单食材整份移动。保留键盘操作、标签和可见焦点，拖动过程中即时更新，不应每次重绘整个编辑器导致失去拖动焦点。

份数与食用克重仍是不同层：存储/分享保留克重；旧保存或分享配方不静默取整。非标准量显示 custom，滑杆可从最近标准位置开始，但只有用户操作后才应用新份量。非法输入不得写入计算结果。

独立工作区改变碗数时，食材与酱料同时按比例放大，每碗营养和价格保持对应关系；不能只改除数导致同一配方被稀释。当前引擎限制 1–12 份、单项总重不超过 2,000 g，重量精度 0.1 g；无法精确缩放的旧自定义量应拒绝，不能静默舍入。

厨房清单列出食材/食物状态、标准份重、每碗份数与克重、整批总克重及建议取用方式。先称重分装，再实际校准勺、夹、泵；没有测试数据，不能声称“一夹一定是 50 g”。这只是测试清单，不是真实订单或已核定 SOP。

## 5 酱料库与必选规则

六种常备候选：Classic Caesar、Honey Mustard、Balsamic Vinaigrette、Basil Pesto、Roasted Sesame、Citrus Mint。另有研发候选 Smoky Chipotle Ranch 和 Sweet Chilli。

每个 Bowl 必须选择酱料。推荐搭配靠前，但允许选择其他候选；未选酱料时不能保存、分享或打开该 Bowl 的完整 Passport 流程。研发酱料在概念试配中可选，不代表可正式订购。

用户明确表示配方尚无定稿，先展示“建议测试配方”。需要酱料照片、建议食材和营养信息位置；当前实际营养未核算，应显示待计算，不能补造准确值。拟配方中的已知食材提示不等于正式过敏原声明，需看供应商标签和厨房交叉接触。

一份酱料沿用各候选现有测试量：20、25 或 30 g，详见 `sauce-content.mjs`。当前 slider 为 1–3 份整份；厨房及封面重量包含所选酱料，营养范围仍按是否量化区分。

## 6 价格演示与真实成本边界

用户要求份数影响价格，并明确授权“先做测试数据，只是演示”。因此已实现虚构加价，不能继续全部显示待核算而不联动，也不能把这些金额标为已核定商业价格。

当前演示按菜单基础目标价加“超出原始单碗配方”的份数费用：鸡肉/金枪鱼每份 +€1.50，三文鱼 +€2.00，猪肉 +€1.75，鹰嘴豆 +€0.50，毛豆 +€0.75，糙米 +€0.50，藜麦 +€0.60，主要蔬菜 +€0.40，菠菜 +€0.30，feta +€0.75，葱/油 +€0.10，芝麻 +€0.15。其他库内新增食材有演示 +€0.50/建议份的回退金额。半份谷物按一半价格。

首份酱料计入演示基础价，额外酱料 +€0.50/份。减少原配方食材暂不给基础价折扣，这是演示实现选择，不是已批准的正式退款/折扣政策。减少之前增加的份数会撤销相应附加费。

例：Rainbow Chicken €8.95 + 一份额外鸡肉 €1.50 + 半份藜麦 €0.30 + 一份额外酱料 €0.50 = €11.25/碗。独立工作区三碗总计 €33.75。逐行四舍五入到分再求和，明细应与总额一致。

滑杆附近持续可见的价格条标 DEMO ONLY；明细标 DEMO PRICING / NOT A QUOTE，并展示基础价与加料项。客户餐品页只显示单碗价；工作区可显示整批价。演示金额不进入真实成本字段、不标 verified，也不是支付或报价系统。

真实模型分开保留每份成本、额外售价及移除抵扣字段，目前未核定。只有显式 `allowDemo: true` 才接受独立 demo overlay。正式定价仍需采购价、可食率、烹饪损耗、包装、人工、费用与定价策略；未完成这些工作，不能把界面演示当作已验证毛利。

## 7 食材库与爱尔兰购买信息

用户希望尽可能多记录爱尔兰可以买到的食材，不限于 Bowl 当前配料，也不局限于一家超市。食材库必须可搜索、分类、按零售商筛选，原料图尺寸统一，蔬菜、水果、谷物、豆类、肉鱼蛋、乳品、坚果籽、香草香料和油酱储藏类清晰分组。

用户指定的检索方向包括 Tesco、Lidl、M&S、ALDI、Donnybrook Fair 等。现有证据另覆盖 SuperValu、Holland & Barrett、Picado、The Village Butcher。必须区分具体产品页、品牌/系列页和门店询问目录：Lidl 鸡肉为系列参考，M&S 与 Donnybrook Fair 当前是单独标识的目录/询问入口，不要伪装成已找到具体 SKU。

每条购买证据保留官方链接、核对日期、包装规格、参考类型以及食物状态/品牌差异。干谷物要煮、冷冻毛豆要准备、罐装鱼要沥干、鲜柑橘需要榨汁，不能把零售包装直接视为配方熟制可食重量。爱尔兰可购买不等于爱尔兰种植，也不等于当前有库存或已确定供应商。

截至 2026-11-19 核对基线：112 种食材、114 条状态记录、33 个追踪营养定义、3,661 条营养观察、114 条图片记录、9 家零售商、120 条购买参考。库仍在增长，并非“爱尔兰所有食材”；当前计数以线上 API/数据库为准，不要把这些快照数字写死成永久产品文案。

## 8 营养信息与排序

用户认为只有数值很抽象，希望读懂食材特点，并能先选营养元素，再按含量降序查看食材。现有功能包括 per-100-g 数值、适用的成人参考百分比、相对库内排名、来源/估算覆盖、营养优先浏览和是否包含参考估算开关。

用户提出 Broccoli Vitamin C 89.2 mg/100 g、“所有食物 Top 2%”作为表达示例，不是已经证明的排名。现有库曾核对为 89.2 mg/100 g、含参考估算时第 7/111、Top 7%；这是特定日期/比较池的例子，不能硬编码，也不能称为所有食品的全球百分位。

排名必须由 PostgreSQL 动态查询：降序、同值并列、包含完整并列组的向上取整 Top 百分比；至少 10 个可比较数值记录才显示百分位 badge。来源值与可选参考估算政策分别计算，已知零值进入比较池，缺失、trace、非数值边界和不兼容单位/基准不能算零或混入。

比较必须匹配同一营养定义、单位和每 100 g 可食基准。原/熟/干状态保持独立；每 100 ml 的记录不能直接当每 100 g。碳水、纤维、叶酸等定义差异保留，不为凑齐数值而混合。分类、搜索、零售商筛选不重定义整个库的营养比较池。

不要用“越高越健康”解释排名。用户问过成人每日最低量，现实现改用成人标签参考 RI/NRV，以及纤维 AI 比较；不是最低需要量、个人处方或必须填满的目标。脂肪、饱和脂肪和盐尤其不应鼓励填满进度条。没有直接可比参考的定义不硬配百分比。

## 9 营养 Passport 与数据缺失

用户曾指出 Passport 全是破折号。修复方向是补齐有来源的食材数据并显示可靠范围，不能通过隐去未知项或把未知当零“补全”。

酱料未定量，所以完整 Bowl 营养仍未知。编辑器及 Passport 显示 Base ingredients only / excludes sauce 的基础食材估算、来源和覆盖；封面总重量包含酱料，需清楚解释重量与营养范围不同。缺失项、trace、参考填充值保留各自状态。

配方变化、标准份快照和厨房批量重量应进入 Passport/完整报告。图片仍是原始份量概念，不随 slider 自动改变，应说明图像不能代表定制后的精确外观。保留下载和打印入口；历史 UI 测试没有实际执行打印对话框，未来改打印须实际验证。

## 10 图片与已选视觉规范

用户要求复用聊天中的餐品图片，给酱料和所有食材加图，强调客人需要直观知道是什么。保留实际图片资产和出处；无法获得未提供的聊天附件时不要声称已经读取它们。当前仓库有复用图、建议配方 AI 图和有许可/署名来源的食材图，相关说明必须可见/可查。

用户先要求白底，偏好黄色、蓝色、紫色，后明确增加红色，并最终选了方案 A / Colour Pop。这是已确定方向，不是待重新挑选的 A/B/C 比较。保留白底、蓝色主动作、黄色选择状态、紫色解释面板、红色品牌点缀、粗体无衬线标题、贴纸/圆形食物拼贴和适度卡片进入/悬停动效。营养数值面板保持稳定易读，颜色不是健康评级。

食物卡片照片保持统一 4:3，不拉伸；手机食材卡为两列，产品/酱料/菜谱卡以易读为先。保留至少 44px 可操作目标、16px 表单字号、清晰焦点、减少动态效果支持、对话框可见关闭按钮及内部滚动。详细设计 token、排版和布局见 [视觉规范](visual-system.md)。

## 11 菜谱保存和分享

保留菜谱浏览、食材来源入口、自建配方、版本历史、复制新原始配方、分享链接和浏览器本地库。当前没有账户同步：清理浏览器数据会移除本地保存；不要承诺云端永久保存或跨设备同步。

分享通过配方编码链接携带名称、份数、食材克重、比较基准和所选酱料。打开后用当前数据重新计算；不能让链接自称获得预设审核或携带未经验证的健康结论。改动份数 UI 时应保持旧链接和保存数据兼容。

## 12 持久数据库与应用结构

用户明确要求迁入持久数据库，不能退回文件拼接假装 live。2026-11-18 已完成 migration 006；2026-11-19 线上核对仍为 `cloud-sql-tables`、114 条数据库食材记录、无静态 supplement 回退。迁移保留旧表与原 view 定义，运行时仍为 SELECT-only。

运行路径：`server.mjs` 提供静态资源和公开 catalogue API；`db.mjs` 使用 Cloud SQL Connector / IAM 读取 `colourfuel_web.catalog`；`persistent-catalog.mjs` 检查持久结构；`menu-formulations.mjs` 组装版本化概念配方；`web-catalog.mjs` 调用 `nutrient-ranking-query.mjs` 的参数化数据库排序；浏览器只使用返回的排序结果。

应用是根目录的 Node/原生浏览器模块项目，不是 React 工程。主要职责：

- `app.js`：路由、食材/营养库、对话框和整体页面。
- `product-content.mjs`、`sauce-content.mjs`：产品、图像说明、饮食标签、酱料及 Passport 展示。
- `recipe-studio.mjs`、`sauce-picker.mjs`：配方交互、滑杆、价格条、厨房单和必选酱料。
- `portion-standards.mjs`：标准份、精确批量换算、真实价格接口及独立 demo overlay。
- `recipe-engine.mjs`：克重校验、营养计算、比较、预设、Passport 和分享编码。
- `nutrition-context.mjs`、`nutrient-explorer.mjs`：参考值解释与数据库排名的前端使用。
- `irish-shopping.mjs`、`ingredient-library.mjs`、`ingredient-photos.mjs`：购买信息、分类、图片及出处。
- `brand-tokens.css`：共享 token；`white-theme.css` 的 shared visual system 区为共享视觉规则。其余样式文件承担既有布局，避免再叠一套互相竞争的主题。
- `public-assets.mjs`：前端资源显式白名单；新客户端模块需加入。数据库/服务端/fixture/部署文件不是公开静态资源。

`previews/colourfuel-bowl/` 是旧副本，不要在那里实施新需求并误以为线上会使用。`fixtures/` 和历史 import 模块用于离线测试或迁移证据，不是生产数据源。不要替换现有 Cloud Run 平台或随意迁移到其他建站平台。
